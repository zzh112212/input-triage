# 分诊判定协议（Triage Protocol）

> SKILL.md 四类分诊表的细则：判定树、各类信号、一行式确认、边界案例、误分类修复。

## 判定树（三问定型）

对每句任务执行期间的插话，依次问：

```
Q1 相关性：去掉这句话，任务结果会变吗？
 ├─ 不会变 ─────────────────────→ NOISE
 └─ 会变 ↓
Q2 意图：它想改变任务，还是只是想知道？
 ├─ 只是想知道（提问/确认/好奇）──→ ASK
 └─ 想改变 ↓
Q3 方向：是往任务里加东西，还是说现有做法不对？
 ├─ 加范围、加需求、加步骤 ──────→ ADD
 └─ 否定、修正、改方向 ──────────→ CORRECT
```

三问全过再行动。任何一问拿不准 → 一行式确认（见下），**不猜**。

## 各类判定信号

| 类别 | 正例 | 易混淆点 |
|---|---|---|
| ADD | "顺便把参考文档也传上去" "对了，还要加个配置文件" | 只是提醒既有要求（无新增）不算 ADD：若提醒的是疏漏，按 CORRECT；若任务已含此事，直接确认即可 |
| CORRECT | "不对，应该用 YAML" "等等，别删那个文件" "方向错了" | "再加个 X" 是 ADD 不是 CORRECT——纠偏一定带有对现状的否定 |
| ASK | "这个报错是什么意思？" "为什么先做这步？" | 疑问形式的建议（"是不是该先做 B？"）更接近 CORRECT，一行式确认意图 |
| NOISE | 与任务零关联的问题、闲聊、感慨 | 用户**重复**说的内容绝不是 NOISE——重复 = 强调，见"重复升级" |

## 一行式确认（不确定时）

分类拿不准，用一句话向用户确认：

- "这句是要并入当前任务，还是先记着收尾再说？"
- "你是想改现在的做法，还是只是问一下？"

默认策略：用户未及时回复或仍含糊 → 按 ASK 搁置（最保守、事后可补救）。**宁可暂存，不可误吸收**——错进任务列表的噪声要靠回滚清理，比补答一条搁置问题贵得多。

## 边界案例

### 元指令（优先级最高，跳过分诊）

用户对分诊流程本身的指令："先别答刚才那个问题""这句不用记""忽略我上一条"——直接遵从。元指令不改任务内容，只改处置方式。

### 连续插话 / 插话纠正插话

逐句登记、逐句分类，**以最后一句为准**（autogoal 冲突协议：最新用户指令优先），但台账把每一句都记全。禁止只看最后一句、抹掉前史——后来的读者需要看到演变过程。

### 插话与既有用户指令冲突

最新指令优先；若与任务早期用户明确要求矛盾，用一句话向用户指出冲突再执行，不静默改向。

### 重复插话（升级信号）

同一件事用户说到第二遍 → 说明第一次被误判或被晾着了。立即升级处理：

1. 重新分类（通常应是 CORRECT/ADD）；
2. 当场处置；
3. 台账记一条"误判修复"。

### ASK 连续积压

搁置区积压 3+ 条 ASK：用户多半已经跟不上任务进度了。主动给一句 30 秒进度简报（"目前第 2/4 步，还剩 X 和 Y"），不展开补答，收尾照常清账。连续求解是沟通信号，不只是待办。

### 答案影响执行的特殊 ASK

极少数求解问题的答案会改变后续执行（如"你刚才为什么删了 X？"暴露了误解）→ 立即补答并按 CORRECT 重新评估当前步骤，不搁置。

## 误分类修复（事后发现分错了）

执行中或收尾时发现某条插话分错了类：

1. 在搁置区/台账该项上标注 `分类更正：<原类> → <新类>`；
2. 立即补救：NOISE 误判成 ASK → 当场补答；ASK 误判成 CORRECT → 回滚多余变更；
3. 保留更正痕迹，不抹掉——**更正记录本身就是任务诚实度的一部分**。

## 本技能不启用的场景

- 单轮问答、闲聊、无任务列表的简短请求；
- 用户不在场的纯自主执行（无插话可分诊，交给 nonstop 一类技能管）。
