# 收尾清账协议（Wrap-up Protocol）

> 任务结束（或阶段告一段落）时：清空搁置区、产出干净台账、完成终局报告、对接交接。

## 触发时机

- 任务全部完成；
- 一个大阶段完成（可做阶段小清账，任务结束再做总清账）；
- 即将交接 / 换窗口（配合 context-continuity）。

## 清账顺序

1. **先 ASK 后 NOISE**：用户等着答案的先还债；
2. ASK 逐项补答：**简短克制**——通常一两句话。用户想要深度解答会说"展开讲讲"；
3. NOISE 逐项处置，三选一：
   - **顺手答**：一句话能答的就顺手答掉；
   - **建议立项**："这句看起来是个新任务的雏形，要开一个吗？"（问，不擅自开）；
   - **礼貌略过**：纯闲聊或已过时的（"刚才那个报错现在还重要吗"），一句话说明为什么略过；
4. 清账完毕，搁置区**无 pending 项**。每项状态只能是 answered / converted / dropped，三者必居其一。

## 干净台账（templates/task-log.md）

**正文只写**：任务目标（含吸收修正后的最新版）、步骤时间线、吸收记录（ADD/CORRECT：原文 → 分类 → 变更）。
**附录才写**：插话处置（ASK/NOISE 去向）、分类更正痕迹。

为什么原文只能出现在吸收记录和附录里：**台账是给下一个会话/下一个读者看的任务真相，不是聊天记录**。混入噪声，恢复者就要重新经历一遍你的污染。

## 终局报告（对用户的最后一条消息）

借鉴 nonstop 三段式 + executing-plans 裁决清单，固定四段：

```
✅ 完成了什么
   <步骤级摘要，与台账一致>

🧭 我做的裁决（ADD/CORRECT 吸收）
   - <决定了什么> — <理由> — <错了的代价>
   （无则写"无"）

📮 搁置处置
   - 已补答：<问题> → <一句话答案>
   - 建议立项：<内容>（等你确认）
   - 已略过：<内容>（原因）
   （无则写"无"）

⚠️ 需要你决定的
   <绕行、风险、开放问题>
```

这四段是**穷举**的：所有裁决、所有搁置项都必须出现，一条都不能静默消失。**终局报告是用户对整次任务的唯一全景视图**（executing-plans 原话：你替用户做的决定，只有这里能到达他们）。

## 交接对接（context-continuity 在场）

- handoff.md 的"已试方案/决策"节直接引用台账的吸收记录；
- 搁置区未清空的项 → handoff.md 开放问题节；
- 新会话恢复后，先重读台账再继续——它比对话记忆可信。

## 验收标准

- [ ] 搁置区零 pending
- [ ] 台账正文无噪声内容
- [ ] 每条 ADD/CORRECT 有裁决记录
- [ ] 终局报告四段齐全且与台账一致
